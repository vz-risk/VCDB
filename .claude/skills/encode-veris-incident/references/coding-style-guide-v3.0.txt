VERIS In a Nutshell
Welcome to the VERIS Coding Style Guide. This document is designed to allow
you to familiarize yourself with the VERIS Framework, and get started in using it
to record the details of security incidents and breaches you encounter. But first,
what is VERIS?
The Vocabulary for Event Recording and Incident Sharing (VERIS) was created to
allow security practitioners to record the details of security incidents and be able
to share that data with others in a standardized, repeatable, anonymous fashion.
This framework underpins the Verizon Data Breach Investigations Report, and is
also used to code cases for the VERIS Community Database Project (VCDB),
where we release publicly disclosed data breach cases coded in VERIS format for
public use.
If you’re just getting started with VERIS, you’ve come to the right place. Here
you will find the information on the schema, with the detailed enumerated lists
and the structure of the 4A’s that are the center of VERIS: Actors, Actions, Assets
and Attributes. Ideally, we would know enough about the incident that we can
identify the values for each of the 4A’s in every case. However, we have found
that with incident response, there are always unknowns. VERIS can handle them
without causing a fuss. We can code as much or as little detail as we have for the
case before us.
Getting started with VERIS can seem rather daunting—it is a complex
framework that has evolved over time as we encounter edge cases that challenge
the schema. However, it doesn’t have to be a complicated ordeal to code up your
first case in VERIS format. For the purposes of all of our training materials, we
are using publicly disclosed cases taken from VCDB data (what we call the
public dataset). For information on where you can see that data and the cases
waiting to be coded, they are stored in our GitHub repo: https://github.com/vzrisk/VCDB. As we encounter new breach reports, we create an issue for them.
As the issues are coded, they are closed and the resulting JSON is placed into the
repo for anyone to use as a dataset.

4

We also have a web application to facilitate coding cases. The WebApp is
available at https://verisframework.org/veris_webapp/#/home. It stores all
data locally, and the output of the case, once coded, is in JSON format. If you
open the WebApp, the first tabs you are presented with deal with basic
information about the incident, the timeline of events and the victim
demographics. Then we dive into the 4A’s. If you are looking for how to use the
VERIS WebApp, you can go directly to that section of this document, but it is
useful to get some background on the 4A’s first.
What are these 4A’s, and how do we use them? They are the Actors, Actions,
Assets and Attributes involved in an incident or breach.

been coding these cases for a long time, but may have questions how a specific
kind of case should be handled. It includes the most relevant fields for each case
type, but not all of the fields in

Actors
Actors are the people who are causing the breach by the actions they take. VERIS
is an actor-centric framework, so identifying who the actor is (external to the
victim organization, internal to the victim org, or a partner of the org) is the
starting point. Some people find identifying the actor a bit confusing. We see
cases where both internal and external actors are recorded, because the logic is
that “the attack would not have succeeded if the employee hadn’t clicked on the
link in a phishing lure.”
That is not how VERIS is intended to work. It is only intended to record direct
actions taken to cause the breach—so the external actor is sending the phishing

6

email, but the internal actor is the victim, not an active, willing participant in the
breach. For there to be multiple actors (and we do see this) they have to both be
working together with the intent to cause the breach. There has to be malice
involved for collusion. If every failure to implement a control that would stop a
breach were counted as an error, it would obscure the actionable causes of
breaches and render the statistics unusable. While it can be argued that there is
always an underlying error in breach causes, it doesn’t drive decisions on where
to put controls if the answer is always “put in every possible control to cover
every possible place an error can be made.” The organization would be funneling
all their resources to security and fail at their core purpose.

A Graphic Approach to Who did What to Whom
VERIS, at first glance, is a complex framework. It can be intimidating for people
trying to deduce what the right answer is for “Who is the Actor?” or “What
Action(s) were involved in the incident?.” To (hopefully) help with that, we have
developed a series of decision trees for people to use to help decide the right
choice for each case. Do you have to use them every time you code a case? Of
course not. But when you are just getting started with VERIS and case coding, it
can help to follow the directed decisions path. And who knows—if you run into
an edge case down the line, it may yet prove useful to even the more experienced
coders.
In VERIS, the Actors, Actions, Assets and Attributes are not exclusive—that is
cases can have multiple selections from each of those categories, rather than just
one. In real life, there is nothing that stops Actors from colluding with each other,
for example, and we want the cases being coded to reflect reality. There is also
nothing stopping the determined attacker from using multiple actions to achieve
their goals. They may start with phishing, and once they have successfully
obtained credentials from their chosen victim, pivot to hacking into a web
application using those stolen credentials. They may then drop malware to
maintain persistence in the environment and shield their actions from detection.
The point here is that since there is nothing stopping the adversaries from using
multiple actions, attacking multiple assets, and violating the confidentiality,

7

integrity and availability all in one attack, the coding framework should not have
those constraints either.
When using our coding decision diagrams (called decision trees), you may need
to go through the paths multiple times to account for all of the details of the case.
In the above scenario, you would traverse the action decision tree several times
to account for the social attack, the hacking action and the malware action. You’d
also need to go through the asset tree several times to account for the Person who
was socially engineered (yes, we count people as assets in VERIS), the User
Device they were using (think laptop) when they were compromised, the web
application the actor hacked into and installed malware on, and then move onto
the Attribute tree to account for those.

Determining the Actor(s)
Determining who the actor was in an incident is not always as straightforward as
it might appear. This is particularly true if you have someone causing a breach
who works for a company that has a business relationship with the victim
organization.
To help with that, we have created a decision tree to guide you in determining
the correct actor. Our first decision is whether the actor who caused the breach
works for the victim organization that experienced the breach. If they do, then
you’re done—it is an internal actor.
If the answer is they do not, then you need to determine if there is a business
relationship involved between the perpetrator of the breach and the victim
organization (at this point, we know they are not the same entity). These are
sometimes referred to as third-party, partner or supply chain breaches, because
these organizations tend to be engaged as part of the normal processes of doing
business. Companies tend to outsource functions that are not their core
competencies, and thus the business to business commerce flourishes.

8

So the question of “Is there a business partner involved” needs to be answered. If
there is such a relationship, then you must determine if the person who caused
the breach works for the company that is providing some kind of product or
service to the victim organization. If the actor works for the partner, then you
have a partner actor breach. If the perpetrator does not work for that partner,
then they are an external actor to the company that they attacked. You then have
an external actor breach, not a partner breach, although the vector may be
partner—more on that in later examples.
VERIS is an actor-centric framework, rather than a data location framework. By
this, we mean that it is the person performing the actions and what their relation
is to the victim org(s) that drives what actor type (and breach type to a certain
extent) you are looking at.

9

In other taxonomies, you may see that there are lots of partner breaches because
they are determining that based on who had custody of the data that was
compromised. We account for that information in our asset list, rather than in the
actor determination.
One question that comes up in determining the actor at the time is if the person
who caused the breach is listed as a “contractor”. How this is handled depends
on the relationship between the victim organization and the person causing the
breach. If they are an individual contractor, like someone hired to do a job
directly, typically someone who is on premises at the company and is treated as
one of the team, we would code them as an internal actor. If the term
“contractor” is used to describe a business where there is an agreement between
the two companies to provide a service, and it is negotiated at the business to
business level, we would consider it to be a partner.

Actions
Once the Actor has been determined, turn your attention to the Actions that were
taken during the incident. Was it a malicious action, like hacking or social
engineering? Was it an accidental action like the loss of a laptop? Intent and
motive play a key role in how these are categorized. For errors, the intent is not
malicious. People do not leave their laptop behind on an airplane with malicious
intent, typically. People do hack into database servers with malicious intent,
however.

Determining the Action(s)
There are many actions in VERIS, so making sure you understand and assign the
correct action(s) to a case is important. Yes, these are non-exclusive and one
incident may have multiple actions (and actors, etc.). It then becomes a matter of
which action came first, and placing subsequent actions in proper order. This
helps later when you are creating the event chain as well.

10

So first we will show an overall decision tree for determining the action. You may
have to go through these decision trees multiple times if there are multiple
actions, but you should be able to figure out which action you should be
recording based on some key decisions about what happened in the case.

11

Each of these decisions end in one of the top-level Actions in VERIS. Once you
have determined which top-level action you are dealing with (and there may be
multiples), then you need to go on to determine the variety within that action as
well. This is where the enumerated lists come in. You can consult the VERIS
framework website for those under each of the 4As to get the values you can
choose from.

Assets
What Assets were involved in the incident? (And notice we say incident not
breach—because you can record those valuable near misses using VERIS as well.)
Was it paper documents? A web server? If it was a social attack, it involved what
we call a “person asset,” so you can record who was the target in these attacks if
you have that information. While we use VERIS for our reporting and research,
there are many organizations out there who use it as part of their security metrics
infrastructure. Knowing who is being targeted in your organization can give you
direction in how to tailor your awareness training.

Determining the Asset(s)
Determining the Asset(s) affected in an incident seems pretty straightforward,
but it can be trickier than it looks. Again, with the others of the 4As, we can have
multiple selections. Certainly, it is not uncommon to find more than one asset
involved in a case—particularly when you realize how common certain attacks
are. Social attacks account for a high percentage of successful data breaches, and
as such, you are at the very least looking at a Person asset.
You also have to account for the device the person was using when they were
persuaded by the threat actor to give up their credentials (or whatever else the
attacker was trying to get them to do). This is most commonly a User Device (like
their laptop or desktop) or perhaps even their cell phone. Then, once you have
identified the initial compromised assets, you need to account for whatever the
attacker did with the results of a successful social attack. Did they gain access to

12

the person’s credentials? How did they use those?

You may need to traverse this decision tree multiple times to account for all the
assets compromised in a case (and remember, it may be a confidentiality
compromise, but there might also be an integrity or availability violation you
need to account for later in the Attributes section).

13

Attributes
Finally, what was the effect on the security Attributes as a result of the actions
taken? We’re talking here about the CIA Triad of Confidentiality, Integrity and
Availability. Many cases involve multiple pillars of the CIA triad. In VERIS,
compromised security attributes are based on the expanded CIA Triad, which
includes Confidentiality/Possession, Integrity/Authenticity and Availability/
Utility. Multiple attributes can be affected for any one asset, and each attribute
contains different varieties.
Think, for example, of an attack that started out as a phishing lure sent to one of
your employees. They fall for it and provide their credentials into a web form.
The attacker uses those credentials against the organization’s web application
infrastructure, and gains access. They then download malware, take a copy of
any interesting data, and trigger the ransomware to encrypt all the files. So you
have a breach of the confidentiality attribute with the data theft, but even before
that, with the credential theft from the phishing attack. You also have integrity
violations with the software installation of the malware, but also because the
social attack caused the employee to alter their behavior and provide their
credentials to the attacker’s web form. Finally, you have an availability violation
when the data becomes obscured by the malware. This was where we would
have stopped, but with the changes in VERIS 1.4.1, we now also record that the
data was abused (in the Confidentiality section), and the interruption of
availability to that data. You can see how one case can have multiple impacts to
the CIA triad. We will get more in depth with a case that is similar to
this down the road, including how the 4A’s would come into play here. When
learning a complex framework like VERIS, we find that the best approach is to
use case examples to show how each kind of commonly encountered case would
be handled.

Determining the Attribute(s)
The Attribute section is where the CIA triad comes into play in VERIS.
Confidentiality, Integrity and Availability are the cornerstones of information

14

security, and when any of the three are violated, you’ll need to account for it.

This decision tree is mercifully short—just the three pillars of the CIA triad.
Confidentiality compromises are the true definition (at least to the DBIR and
VERIS) of what a data breach is. Someone who was not authorized was able to
view (which includes taking a copy of) data at some point in the course of the
case. We also have an option to mark Confidentiality as “At-risk” for cases where
it is suspected, but cannot be confirmed. The stolen laptop is an example where
making that confirmation is quite a challenge. But it is definitely at-risk, since the
owner has lost custody of the device.
For Integrity, things get more complex. The Integrity of an asset indicates that it
reflects reality—that no changes are made to the system that are unauthorized. So
even when the asset is a person and they are influenced to do something they
should not be doing, it is an Integrity violation (alter behavior). The same goes

15

for a computer where someone installs malicious software (whether it is on disk
or just exists in memory), Software installation is the violation in this case. There
are a large number of ways to violate the integrity of a system—even changing
the data or configuration files would be a violation.
Initiating fraudulent transactions (think money transfers) is also an Integrity
violation, as is impersonation. If an attacker compromises an executive’s email
account and sends an email to the finance worker to have them pay a fraudulent
invoice, you have multiple integrity violations. In contrast, some integrity
violations are physical in nature—putting a skimming device on an ATM is a
good example. That would be considered tampering.
Finally, we have availability violations. If an asset is stolen, we lose access to that
asset. Likewise, if the data on a server is encrypted by ransomware, we lost
access as well. Denial of Service attacks that bring down infrastructure ensuring
the legitimate traffic cannot reach it is another example of an Availability
violation. When you look at the enumerations for each of these attributes, you
can see why the list is so comprehensive. Most of them have come about from
actual cases that were coded by the DBIR team.

The VERIS WebApp
Having introduced you to the building blocks of VERIS, it is now time to dive
into coding real cases. VERIS is widely adopted, and many organizations use it
in their own environments. While the implementation may differ, the
commonality is using VERIS to describe each of the data points captured. Some
use spreadsheets, or their own case management platforms to do this, depending
on their infrastructure. But if you are just getting started with recording the
specifics of the cases you work, and don’t already have a process built, we can
help.
Allow us to present the VERIS WebApp. It is a standalone application that you
can use to fill in the details of each incident, and when you finish, export the
JSON to your local hard drive. To be clear: this application does not send your
data anywhere unless you tell it to. You are in control of the data that is exported
from the application, and if you delete the data out of the application without
first exporting each incident, it cannot be recovered.
We understand that this is sensitive data, and we just want to be certain the users
of the application understand they are in control of the data they enter. That said,
this is a great little application that lets you use form fields to get as detailed as
you need to when coding an incident. It exports each case as a standalone JSON
file, which can then be used as you choose.

Creating a New Incident
As mentioned earlier, you can access the VERIS WebApp via https://
verisframework.org/veris_webapp/#/home. When you first launch the page,
you will be presented with a basic interface with two options: Creating a New
Incident or Importing Existing Incidents.

Of course you can create new incidents, and this is likely to be what you use
most often, but there is also an option to import JSON incident files that have
been formatted according to the appropriate schema. We will get into that more
in the Things Change, Incidents Evolve section. For now, let’s assume you’re
going to start from scratch and code your first case in the WebApp.
When you click on Create Incident, you are shown two dropdown menus: the
Schema and the Version. You need to choose the schema type. Your choices are
listed below.

18

For the purposes of this Guide, we are using the VCDB schema. This schema is
used when coding incidents in the public dataset—the VERIS Community
Database, where we code up publicly disclosed data breach reports (from various
sources) and release the dataset to the public. More info on that project can be
found here: https://verisframework.org/vcdb.html.
The other schemas listed are as follows:
• Partner: this is used by organizations who are planning on submitting data for
inclusion in the Verizon Data Breach Investigations Report (DBIR). It does not
contain fields that would identify the victim organization, as we do not collect
that information for the report.
• VERISC: This is used by organizations who are implementing VERIS in their
own organizations. It allows them to capture relevant information that will not
be shared with Verizon for the DBIR.
• DBIR: This is the schema the DBIR team uses to code cases from our forensic
practice. It is not a schema that is available outside of the team.
• VCDB: This is the schema the DBIR team uses to code publicly disclosed data
breach incidents from the VERIS Community Database repository on GitHub. It
has fields specific to that use, including the GitHub issue number, URLs we used
when coding the incident, and more importantly, victim organization identifying
information. This dataset is the only one where the victim organization is
recorded. If this is something you want to record in your use of this WebApp,
then this schema may be a fit for your needs.

The Incident Info Tab
When you have created a new incident, this is the first tab you will encounter. It
is for entering the basic information about the incident that is needed for each
case.

20

The Security Incident drop down allows you to record if this is a confirmed
security incident (defined as violating one of the pillars of the CIA Triad), a near
miss or a false positive. You can choose “Suspected” if you are unsure, but want
to record the details in case something develops in this case later. Once an
incident is created and exported as a JSON file, you can always import it into the
WebApp for later updates.

21

The Reference field is where we list the URLs we used in coding this incident. We
separate them with semi colons.
The Summary field is where you record (in general terms) what happened. It
should be long enough to stand on its own and let someone who is reading it
know why you made the choices for Action, Actor, Asset and Attribute in the
JSON. If all the referenced URLs become stale, this summary should be enough
to justify why a case was coded the way it was.
The Source ID field is used to let us know where this incident came from. For our
purposes, this is a VCDB case, so we use that as the value. If you were
implementing this in your own organization, you might want to use the
department or division of the organization where the incident was discovered, or
most affected. It is a free text field, so use it as you need.
We include a Campaign Id for those cases where we want to be able to tie
multiple victims of the same attacker(s) together as a campaign. Confidence lets
your analyst indicate how confident they are in the data they are entering. When
working with the public dataset, we sometimes have less confidence in the data
than say a case coming from a forensic firm. This is how we weight that in our
dataset.

22

Analyst Status is showing the phases an incident goes through to be included as
a validated incident in our corpus. You may or may not want to utilize this if you
have some kind of review process for your incidents. The Analyst field is the
person who coded the case. We use GitHub Ids for this field, but you can use
whatever works for your organization’s needs. There are notes fields for case
notes and for anything the analyst wants to communicate to someone reading
this incident in the future. And finally, the DBIR Year is used by the DBIR team to
show which report’s year this case should be included in. This is because cases
may not be discovered for several years, and there will be a different year for the
timeline of the incident versus when the case came to light and was investigated.

The Victim Tab

For our purposes, we have the organization’s name, their NAICS code, number

government, but the scope tends to remain similar.

A Note about NAICS
We on the VERIS team use the North American Industry Classification System or
NAICS codes to designate an organization’s industry membership. Some of the
NAICS codes are quite straightforward, like Healthcare (62). It is easy for most
companies to know if that is where they would belong, and to make sure they’re
looking at the right industry when they read the DBIR statistics.
However, there are a number of the NAICS codes where the grouping is very
widely distributed, and it may be difficult for people to know for certain where
they should be looking. To that end, this is one of the most straightforward
references for what kinds of organizations are in each of the NAICS industries.
http://www.farsmarterbids.com/reference/naics-list.php
One example we ran across was the Arts, Entertainment, and Recreation (71)
NAICS code. It is made up largely of live performances, rather than those that

The Action Tab
Now the tabs start to mirror the 4A’s of VERIS. In the Action Tab, we can
document all the actions that were taken during the course of the incident.
Understand, as in life, there is no limit in VERIS to say that only one action can
happen (or one Actor, etc). Since incidents can be quite complex, the framework
allows for the same flexibility in recording exactly what happened.

31

We are starting with a simple case having only the one action, so we only record
that. As you move through the tabs, we encourage you to take a look at the
options in the other drop downs to familiarize yourself with how VERIS works.
For our case, we know the action was Hacking, Use of stolen credentials. We
know this was against a VPN based on the reference articles, and we know that it
allowed the attackers to both infiltrate the system and exfiltrate the data. There
may have been other actions, but the articles do not talk about them, so we
would be guessing, and we try not to do that.
Do we know how those credentials were compromised? Not with this reference
material. It could have been the result of a social action such as Phishing. It could
have been another hacking action such as Brute force. It could even have been
acquired from an unrelated breach and be an example of credential reuse. We just
don’t know, so we leave this record with the data we do know and don’t
speculate.

32

The Actor Tab
The Actor tab is all about the “who dunnit” part of the case. For publicly
disclosed data breaches, we rarely get a high level of detail here. Attribution is
difficult in investigations, and while there are many threat actors who make it
easy by announcing to the world that they are responsible, we cannot rely on that
kind of convenience.
“While crucial details regarding the cybersecurity incident were unavailable, including the
threat actor’s identity and how the VPN credentials leaked, a Park ‘N Fly spokesperson said the
data breach affected “1 million customer files.””

For our purposes, we don’t know the variety, but we can infer it was done for
financial gain. Attackers going after this volume of customer data are not
typically doing this for funsies.
You can add data if you have it on the region the Actor is from, and the name.

33

The Add item buttons will give you more fields if you have multiples to add.
Whether the actor(s) are External to the victim organization (no business or trust
relationship), Partners (some business or trust relationship) or Internal
(employees, contractors, etc. Trust is in place for them to do their jobs), or some
combination thereof, you can include as much detail as you have. In cases where
there are multiple actors, take care that you are not including actors “because
they didn’t do something best practice indicates they should have”. This is for
overt actions that contributed to the breach. We do not include “they didn’t patch
a vulnerability” as an Error action, for example. That is a rabbit hole that tends to
muddy the statistics when looking at data breaches.

The Asset Tab
The Asset tab lets you record the information asset (including people for Social
attacks) that were affected by what the perpetrators did to cause the breach.

The Total Amount box is recording the total number of assets affected in the

34

breach. You can also fill out the detail in terms of which assets had specific
numbers affected, but you will have to do the math to include it in the Total
Amount—this is not a calculated field. This is largely because while there may be
detail about some of the affected assets, it is common not to have specific
numbers about all of them.
The asset of S - Remote access server is how we categorize the VPN system that
was compromised in this breach. Given the high number of customer records,
we also choose S - Database, which tends to be where large datasets are stored.
Certainly, we don’t think there was a set of a million customer records sitting on
the VPN server (at least we hope not!).
As with the prior tabs, the Add Item button allows you to add more fields so that
you are not constrained when recording the number and type of Assets involved
in each case.

Some time ago, the DBIR team started recording whether Cloud infrastructure
was involved in breaches, and starred fields are required. We do not know the
status of the systems compromised in this breach, so that is left Unknown. We
also collect data on whether the asset roles were IT, OT or something in between,
but this is also not a required field.
If you have the information (and are interested in tracking it) you can record that
operating system the affected asset runs. You can also record the country where
the asset resides. These may be data points that are important to your
organization in tracking trends.

The Attribute Tab
As mentioned previously, we track how each of the pillars of the CIA Triad are
affected
in security incidents. This is tracked in the Attributes tab.

Confidentiality
We know that Confidentiality was confirmed as compromised, given the
attackers exfiltrated 1 million customer records. So Data Disclosure is marked as
Yes. This is a required field—but the value can change. The Data Total box is
where you indicate how many records are involved. The Data Victim allows you
to track what kind of records were taken, and what the relationship between the
victim organization and the subject of those records is.
Under the Data Varieties, you can add as many as needed to record the quantity
and type of records affected. This has allowed us to run statistics looking at only
one kind of record—such as medical data from patients. VERIS allows you to get

36

as granular as your data is, so you can gain robust insights into your own
organization’s security status.

The Data state box is tracking if the stolen data was all in the clear, or if some (or
all) was encrypted. It is good for scoping the breach and recording in this manner
what percentage of the affected data is actually at risk.
The Data Abuse field is to document if there are known cases of the data being
abused by the adversary. If there is evidence of fraud, for example, or if the data
was subsequently put up for sale on the dark web.
You can also record if the victim organization offered credit monitoring to the
data victims, and if so, for how many years.

Integrity
Although we do not have an Integrity violation in this case, you can always take
a look at the Variety dropdown to see what the options are. Some common cases
are software installation, for malware cases, and alter behavior for social
engineering actions.

Availability
The same is true for the Availability section—commonly seen in Denial of Service
attacks, as well as ransomware cases, where the data was encrypted. You will see
examples of both of these types of cases in the Templates in Action section.

The Targeted Tab
This tab is pretty straightforward. You can record (assuming you have this data,
it can be quite difficult to come by) if the attack was specifically targeted at the
victim, which implies the victim was chosen before the attack was laid out.
Alternatively, if the attacker had an exploit they knew worked and were just
looking for victims they could use it against, it is not a targeted attack, but an
opportunistic one. Accidents of course are not applicable, since there is no malice
involved. Targeting is by nature a malicious action.

In many cases, we simply do not have this information, but it is an included field
in case we do.

The Discovery Method Tab
The Discovery Method tab is a great way for organizations to record which of
their controls are catching intrusions. It speaks to effectiveness of controls, and
visibility into what is going on in their environment.

Your choices here are External, Internal and Partner, with the associated varieties
to choose from. These work just like the Actors do—with levels of trust implied
by their role. It stands to reason if you have to wait for someone who is outside
of your organization to tell you that you have had a breach, it is likely to have
been going on for longer than you’d like.
While this case example doesn’t tell us how the breach was discovered, we do
have some good options to choose from when we do have that data. All of these
are non-exclusive, so if a breach was discovered in multiple ways, you can record
that.

The Value Chain tab is used to track the pre-event activities required for the

We don’t have this information for the case we are using, but there are a wealth

The Impact Tab
The Impact tab attempts to capture some of the information that is useful when
trying to assign a value to the impact a breach has had on an organization.

You can set your own criteria, and assign impact ratings to the various data
points. While a lot of this kind of data isn’t available when the incident first
comes to light, after time has passed and cases make their way through the court
system, some of this data can show up.
This is particularly true of regulatory fines, or class action (or single action)
litigation settlements. These are some of the easier impact data points to capture.
This, along with the cost of responding to an incident can be recorded for internal
incidents in particular.

You can track metrics on how difficult you think the attack was to implement.

The Event Chain Tab
Finally, we come to the Event Chain tab. This is where we in the DBIR team

You can add items to make the event chain as complex as you like, and reorder
them using the up and down arrows.
For our case, we have two events. The first is when they used stolen credentials
to access the VPN server. The second is for the data exfiltration from the

This is the last tab before the case is ready to export. There will be a validation

Using Templates to Code Cases
Faster
What are Templates?
Over the years, the DBIR team has coded hundreds of thousands of cases. In that
time, the team has tried to find shortcuts to what can be a tedious and time
consuming process. As we have found common themes in our data, we have
created the following templates or blueprints of cases we encounter again and
again. The goal with these templates is to help automate some of the more
common case coding, and we are hoping to achieve about 90% of cases falling
into one of these templates. Some of the details will change on a case by case
basis—these are the variables that you need to fill out. These templates have been
organized by the Action/ Actor combination with additional details on varieties
as needed.
Template files can be found on https://github.com/vz-risk/veris.
We recommend you work from a copy of the template files on your local
machine. You can import the template you need just as you would any other
JSON case file. You can then edit the details to match your case, but the main
action, actor and other key fields are pre-populated for you. This can be quite a
time saver when coding cases that fit the template you have chosen.
NOTE: Our WebApp is currently experiencing a known bug where the master_id
does not change when you import a case and save it or copy/ duplicate it inside
the app. So if you are using the master_id in your processes as a differentiator or
unique id, you will need to change that value manually in the JSON before you
ingest the files for each file you generate this way. It is a simple
matter to have a new uuid generated (an example site that does this for you is
https://www.uuidgenerator.net/.)

48

We established many templates for you to use for each of the common case types
we have identified. As we encounter new common case types, we will add the
template into the same repository. If you have a case type you encounter quite
frequently in your own experience, you can simply save your own templates as
well for future use (A template is just one of the common case type JSON files
with some of the fields that usually change not filled in, nothing magical here).
We have started using these template names as tags on VCDB issues, which is
where we keep our publicly disclosed data breaches awaiting their turn at
coding. If you would like examples of cases that apply to each template, you can
always go to the issues list on GitHub (https://github.com/vz-risk/vcdb/
issues).

49

Then click on the tag name for the template you are interested in:

And you will see the subset of issues corresponding to that tag. You can then drill
into the articles identified for that issue. This is a good way to get familiar with
the kinds of issues that would apply to a particular template.
While writing this version of the Coding Style Guide, the big Salesloft Drift
campaign was going on, so you can see there are a lot of incidents that
correspond to that template tag.

50

The template naming convention is as follows: Action-Actor-Action.variety and
then another detail that differentiates it from the other similar cases. So if you
were working a case where a hacker got in by exploiting a software vulnerability,
you would use Hacking-ext-exploit-vuln. For a ransomware case where there
was no data disclosure component, you would use Malware-extRansomware-nobreach.
The differentiator is sometimes what asset was involved, or whether there was a
breach of confidentiality, or some other special characteristic that has made it a
case type that we see enough to warrant it’s own template.
With all of these templates, the goal is to get you most of the way towards a
coded case, with just the variables that change from case to case needing to be
filled out (such as victim demographics, the asset(s) involved, discovery method,
and any other field that doesn’t match your reality for the case you are coding. It
is faster to change a few things than to have to code each case by hand from
scratch.

Error Templates
Our Error action templates are grouped together by who the actor is that causes
the breach, the kind of asset involved, and the attribute that was compromised as
a result.
Error actions can either be caused by internal actors—those who have either an
employment or some other trusted relationship that grants them access to the
organization’s premises and systems to do their jobs; or partner actors—those
who, because of a business arrangement with the victim organization have access
to data or assets, but are not typically behind the victim organization’s internal
controls.

51

Internal Actor Templates
Error-int-disposal-paper: Paper documents are disposed of improperly.
Example: something that should have been shredded was just tossed in the trash.
The person who threw away the documents was internal to the victim
organization.

We see this case less frequently than we used to. There was a time when paper
documents were being disposed of in the trash despite the data they contained
being protected by breach disclosure laws. Most of the organizations these days
have received the memo that shredding paper is a good practice.
Error-int-disposal-usrdev: A user device is disposed of improperly. Example: an
unencrypted laptop was thrown in the trash. The person who threw away the
laptop was internal to the victim organization.

52

When user devices are disposed of with all their data still on them, hilarity
ensues. Well maybe not really, but we have seen many cases where the assets end
up for sale on eBay instead. Then someone buys them and finds a treasure trove
of confidential information.
Error-int-loss-paper: Paper documents are lost. Example: Sensitive printed
material are left in the seat back pocket of an airplane by mistake. The person
who lost the documents was internal to the victim organization.

53

Error-int-loss-usrdev: A user device is lost. Example: A laptop computer is left
behind on the bus. The person who lost the device was internal to the victim
organization.
Note that when the disposal was botched, we don’t show an availability loss.
But when a device or media is lost, we do have to account for it. This is because
we believe that if the asset is being disposed of, the data should already have
been copied elsewhere if it was important.

54

We have the template for the loss of a user device (typically a laptop, but change
the variable value as needed in the app). You can see a lot of the values will
remain constant across the cases of this type. A difference here for the user device
of a laptop is that since data disclosure is at risk, we don’t record a confidentiality
loss in the event chain. We do still record the availability loss of the device,
however.
The Discovery method will typically being the employee realizing that they no
longer have the asset they were supposed to be keeping track of. If the laptop
was encrypted, for example, you would want to change the Confidentiality to
No, unless of course the passphrase was written on a sticky note and kept with
the asset. Don’t laugh, we’ve seen it multiple times.

55

Error-int-misconfig-srv: A server is misconfigured, and most frequently, the data
is discovered by a security researcher.

This is the template for all of those security researchers using their specialized
search criteria to find the data stores that someone stood up on the internet
without any controls to protect it. While we find this less often over time than we
used to, since many of the vendors whose infrastructure this uses have instituted
defaults that require controls before deployment, there remain many of these
nuggets of data just waiting for someone to find. On the internet, there is no such
thing as “flying under the radar.”

The Hacking action is most commonly an external actor—and all of our Hacking

Hacking-ext-bruteforce: A threat actor who has no affiliation with the victim

Hacking-ext-defacement: A threat actor who has no affiliation with the victim

69

Defacements seem to ebb and flow with the volatility of the times. They are
frequently perpetrated by activists with an axe to grind, whether against the
owner of the website, or just a target of opportunity, where they knew an exploit
that worked on that site.
These are frequently breaches of the system data if nothing else (they likely
looked around at their victim’s systems to see the layout of the land), but
sometimes they also take data from the victims. They like to remake the website’s
home page in their image, so to speak, and may cause the site to crash as well.

breaches—no data is compromised. These are primarily Availability attacks

designed to degrade the performance of the victim’s systems, or ideally—from
the attacker’s standpoint—knock them off the internet entirely. Thus we most
commonly see these cases being valid security incidents, but not data breaches in
VERIS terms. There are a very few cases annually where we see the attacker take
the data, and if you are using this template file, you would just change the value
of the Confidentiality attribute in the WebApp.

Sometimes the best way to learn how to use something is just to dive in. You’ve
seen the templates we provide, and now it is time to actually use a template to

Whether you choose to do this by making a copy of the whole template directory,
or just a copy of each template before you use it is entirely up to you.

For this example, we begin at the Home screen with no cases listed. Obviously,
you can do this regardless of what state your Home screen shows (a list of cases
in various states, or blank like ours). We need to import a template before we can
use it, so click on the Import Incidents button.

It is up to you how you want to use this, some like to import all the templates at

once (or all the templates of a specific kind of incident, such as all the Error
templates), and others like to import just the template for the case in front of
them at the time. Either way, start with the Import Incidents button.

drop files onto the appropriate blue section of the Home Screen.
NOTE: As indicated in the Things Change, Incidents Evolve, there is a limit for

Clicking the Browse files will bring up a dialog so you can navigate to where you
have stored your template files.

For our example, I will choose the Hacking-ext-stolencreds Template.JSON file.
The template is just a JSON file of a sample case coded where the action was
Hacking - Use of stolen creds, the actor was external. This will load that sample

Now that the template is in your case list, you can edit it with the pencil icon

Summary field.
As you go through the various tabs, make your changes, paying particular

will now have your JSON file ready to be renamed.

Victim Demographics
As mentioned in the VERIS Overview section, we record victim demographics
(when we can get them) for each incident. They include fields such as the name

of the victim (for VCDB cases), the organization’s size (in terms of how many
employees) and their industry. We really like to have the last two whenever
possible, since these are two of the ways we commonly split out the data in the

We also record what country the victim organization resides in (and if it is

create a record for each of their customers (see Third party or Supply Chain
Breaches).

Are all of these encountered regularly? Not so much. Most common are the Loss,
Misconfiguration, Misdelivery, Publishing and Disposal errors. The others come
up now and again, but some are quite rare.
We have case examples from the common Error types where we go into detail for
each case. Let’s move into those.

Disposal
Disposal errors occur when either electronic or paper assets are disposed of
without taking into consideration the need to protect the data on them. For paper
documents, the typical solution is to shred the documents prior to disposal, or in
some cases, this is performed by a partner vendor for an organization under
contract. Paper documents are the special case in that we consider any time they
are lost (or stolen) it is considered a confirmed compromise of the confidentiality
of the data printed there. The person who finds them typically has to read them
to even realize they contain sensitive information, and there is simply no control
that will combat the vulnerability.
Our first case example is the disposal of paper documents. You can see the Victim
Demographic information we most want to have filled out. We tend to split our
data along organizational size, industry and regional lines, so we like to have
that information. If you are working on implementing VERIS in your own
organization, and there are multiple locations, it is nice to see where the hot spots
are as well.

Publishing
A publishing error occurs when private data is put on a public facing website
and is somehow accessible to the world. The website is then indexed by the
helpful search engines and frequently comes to light when a customer googles
themselves and finds their data flapping in the wind. We typically find this as a
result of some change control process failure, where the site’s controls were
suspended to make some kind of change, and then after it was completed, the
controls were not put back in place.
It also occurs when unsanitized private data that should not have been uploaded
gets put on a site that is open to all.
“A police activity log for the period of January 7 through January 13 was
published on the Littleton department's website. Someone forgot to remove
personal details from the log and the sensitive information was available online
for 10 days. Names, Social Security numbers, dates of birth, and addresses, were
available between January 14 and January 24.”

Malware Overview
Our first example is a standard ransomware case. Until recently, these cases were
treated as incidents, not confirmed data breaches, unless there was a compelling
reason to treat them otherwise. However, since November 2019, certain groups of
ransomware attackers have changed their tactics to take a copy of the data prior
to triggering their encryption routine and then using the threat of data exposure
as leverage to encourage victims to meet their ransom demands. So we will show
an example of a standard ransomware case, as well as a case where data
confidentiality has been confirmed to be compromised.

Ransomware
For Ransomware cases, we have a decision to make: was there a data breach or
just the malware infection? We have split the two case types out to show how
both should be handled. In general, if there is no indication of a confirmed
compromise of the confidentiality aspect of the data, then the case should be
coded as not being a data breach, but just a security incident.

Ransomware with no confirmed breach
Ransomware has been a popular money maker for bad guys on the internet.

Pretexting
The Business Email Compromise is a lucrative social engineering attack that has
increased in frequency in recent years. It is usually based on a pretext social
action—when someone invents a plausible story to get the target to take the bait.
“In October 2017, someone infiltrated the email of the president of Buresh
Building Systems and used the account to direct an employee to wire money to
an account of K Henao Elite Inc. at SunTrust Bank in Florida, according to court
records.
Company officials later determined the president’s email account had been
accessed, and the perpetrators had set up systems within the account to hide the
fraud-related messages when the president was using the account.”
This turns out to be a fairly complex case. First we have the standard
demographic info that we try to collect from all cases. We have a confidentiality
violation with the stolen credentials from the executive from the first phishing.
“The organization allegedly gained access to email accounts of business leaders
through a “DocuSign” rouse — emails told users to sign into their accounts and
reset their passwords. Then members of the group imitated the business officials,
asking workers to wire money to bank accounts they controlled and then sending
the proceeds overseas.”
So they got the executive’s credentials via their DocuSign phish, and used them
to get into the email server—that is our confidentiality violation. They then made
changes to the email account’s rules to keep the executive from knowing their
email account was being used to send further social attacks. They misrepresented
themselves as the legitimate owner of the account, and they used a pretext to get

154

the employee in Finance to make a fraudulent transaction, sending them money
to the account they controlled. So we have three integrity violations once they got
the credentials.

Coding Multiple Actors/Actions
When different types of actors get together, it never means good news for the
victim organization. As with multiple actions, VERIS allows for multiple actors
to be active in a breach. VERIS has three actor types: Internal, External and
Partner. When we see multiple actor types, there is sometimes a social
component where the external actor recruited an existing employee, or even sent
someone into an organization with the goal of getting hired and having access to
data. Partner actors may also be either the recruiter or recruited.

telecommunications companies (yes, ours was one) to use their access to gain

“Internal actors at Verizon & AT&T collaborated with external actors to misuse

Third Party or Supply Chain Breaches
Once you have been coding publicly disclosed data breaches for a while, you will
start to see cases where it is a widely used third party service that was
compromised, resulting in all of their customers having to report data breaches.
Rather than coding each of those customers as a separate breach, we handle them
a bit differently. We code them up from the partner’s perspective rather than the
customer’s perspective, and we do that for one very important reason: we don’t
want to artificially inflate the data breach count for that time period. If you think
about it, this is really just one actual breach—this isn’t attackers having to go
from company to company and breaking into each of their systems/bypassing
each of their infrastructure controls one-by-one. No, this is one actor breaching
one infrastructure, and scoring data on lots of different organizations in a
business-to-business relationship. So to avoid making the problem bigger and
more complex than it really is (and it is already complicated enough, thank you
very much), we code it from the perspective of the partner, and list all of the
organizations that were affected in the Secondary Victim_ID field, along with
their industries.

Third party breach vs. Supply Chain
In December 2020, Reuters reported on the SolarWinds data breach, and people

166

began talking about Software Supply Chain and the risks illustrated in the
compromise of infrastructure that is widely used across industries. For the
purposes of the VERIS Coding Style Guide, we define these two terms as follows:
Third party data breach: data is compromised of others, but not their
infrastructure.
Supply chain data breach: downstream infrastructure is compromised in
addition to the data of the customers of the victim organization. Subsequent
action against the initial victim’s customers is taken by the adversary. Supply
chain: partner is the vector; third party: partner is the data type compromised.

Example 1: Click2Gov/Superion Third Party breach
This case has become something of a legend in the VCDB dataset. The vendor
serves a large number of government entities—particularly at the city level. They
are used by a variety of city agencies to handle payment card processing and
records keeping for the city constituents to access the services offered by the
municipality. When this company was hacked, we first saw a wave of their
customers announcing the breach.
Usually for these partner breaches, we hold off on coding the case until there has
been sufficient time for the affected customer organizations to all report the
breach and notify their own customers that their data was compromised. This
case is a bit of a puzzle to us, because while there was that first expected wave of
notifications, after they had died down and we thought it was about time to code
the case up, suddenly a second wave of notices hit. Was this the same breach
only they found more victims? Did they take a phased approach to their
notifications? We don’t really know.
But wait, there’s more. After that second wave died down finally, and we dared
to hope we could code this up (we did actually code the first wave which is why
you have a JSON record in our diagram title), suddenly there started up a new
round of notices. Now we’re waiting some more to code the second wave and

time, we are inclined to call this a separate set of incidents, but we as a team will
have to argue that one out before we code it.
